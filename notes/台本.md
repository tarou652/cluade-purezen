# プレゼン台本 ―「Skill ― AIに"やり方"を教える技術」

> スライド1枚につき台本を1つ。各スライドは「スライドに載せる内容（箇条書き）」＋「台本（実際に話す言葉）」で構成。
> 想定: 社内エンジニア／同僚向け・15〜20分・ゴールは「自分でもスキルを作ってみたい」と思ってもらうこと。

## スライド1: タイトル

**スライドに載せる内容**
- タイトル: Skill ― AIに「やり方」を教える技術
- サブタイトル: どんなモデルでも同じ品質を引き出す仕組み
- 発表者名 / 日付

**台本**
本日は「スキル」という技術についてお話しします。AIは賢いのに、なぜか毎回こちらが手順を細かく指示しないとうまく動いてくれない——そんな経験はありませんか? 今日紹介するスキルは、その問題を根本から解決してくれる仕組みです。最後にはぜひ、皆さんにも「自分でスキルを作ってみたい」と思ってもらえたら嬉しいです。

## スライド2: ハーネスエンジニアとは?（本には載っていない導入）

**スライドに載せる内容**
- ハーネス＝「つなぐもの・支える枠組み」
- ハーネスエンジニア＝どんなモデルでも同じ品質の出力になる"環境"を作る人
- AIを賢くするのではなく、力を安定して出せる土台を作る

**台本**
本題の前に「ハーネスエンジニア」という言葉を紹介させてください。本には載っていない、最近よく聞くようになった考え方です。ハーネスとは「つなぐもの・支える枠組み」という意味で、ハーネスエンジニアとは、どんなAIモデルを使っても同じ品質の出力が得られる"環境"を整える人のことを指します。AIそのものを賢くするのではなく、AIが安定して力を発揮できる土台を作る人ですね。今日のスキルは、まさにそのための代表的な道具なんです。

## スライド3: 課題 ― AIは賢いが、毎回手順を書かないといけない

**スライドに載せる内容**
- AIはタスクの"意味"はわかる
- でもタスクの"やり方"はわからない

**台本**
では本題です。まず、私たちが普段感じている課題から。AIはとても賢いですが、ひとつ弱点があります。「タスクの意味はわかっても、そのやり方はわからない」ということです。たとえば「議事録を作って」とお願いすると、議事録が何かは理解しているけれど、うちの会社のフォーマットや手順までは知りません。だから毎回、こちらが細かく手順を説明する必要があったわけです。

## スライド4: これまでの解決策と、その限界

**スライドに載せる内容**
- 長いプロンプトを毎回書く → 大変
- よく使う指示を command 化 → 楽になった
- でもモデルが変わると出力品質がブレる

**台本**
この課題に対して、これまではどうしていたか。最初はとにかく長いプロンプトを毎回書いていました。それが大変なので、よく使う指示を「コマンド」としてまとめるようになります。ただ、それでも問題が残ります。AIが進化したり、モデルを変えたりすると、同じ指示でも出力の品質がブレてしまうんです。「昨日はうまくいったのに今日は違う」という、あの不安定さですね。

---

## スライド5: 解決策 ― Skill

**スライドに載せる内容**
- スキル＝AIに「やり方」そのものを教える
- いつ・誰が使っても同じ品質の出力
- プロンプトを毎回書き直さなくていい

**台本**
そこで登場するのがスキルです。スキルを使うと、AIに「タスクのやり方」そのものを教え込むことができます。手順をあらかじめ定義しておくので、誰が使っても、いつ使っても、同じ品質の出力が返ってくる。毎回プロンプトを書き直す必要もありません。これが今日いちばん伝えたいポイントです。

---

## スライド6: MCPサーバーとの違い

**スライドに載せる内容**
- MCP＝AIが外部サービスにアクセスするための"接続方法"の一種（他にCLIなど）
- 弱点①: 接続できても使い方がわからない
- 弱点②: 通信のたびツールを選び直すので遅い
- 弱点③: アクセスが多くトークン消費が増える
- 背景: AIがOS操作できなかった時代の技術

**台本**
ここでよく比較されるのが「MCPサーバー」です。MCPは、AIがさまざまな外部サービスにアクセスするための"接続方法"のひとつです。便利なのですが、弱点もあります。ひとつ、接続はできても「使い方」まではわからない。ふたつ、通信のたびにどのツールを使うか選び直すので、動作が遅くなりがち。みっつ、何度もアクセスするのでトークン消費が増えてしまう。これは、MCPがまだAIエージェントがOSを操作できなかった時代に生まれた技術だから、という背景があります。

---

## スライド7: Skill ＋ CLI という組み合わせ

**スライドに載せる内容**
- CLI＝必要な操作だけを最小の手数で実行できる
- その手順を Skill で定義 → 相性が良い
- メリット: トークン削減 ＋ 品質が安定（ブレない）

**台本**
では、その弱点をどう解決するか。答えが「スキルとCLIの組み合わせ」です。CLIを使えば、必要な操作だけを最小の手数で実行できます。そして、その操作手順をスキル側で定義しておく。この2つはとても相性がよくて、トークン消費を抑えられます。さらに、自前で用意したものを実行する形になるので、AIに毎回コードを書かせるときのような"ブレ"がなくなり、品質が安定します。だから、正確さが求められる処理にも安心して使えるんです。

## スライド8: Skillの中身を見てみよう

**スライドに載せる内容**
- 構成: 概要（YAML）＋ 本文（Markdown）
- AIはまず"概要"だけ見て「使うか」を判断
- スキルが増えても最初に読むのは概要だけ → トークン節約

**台本**
では実際にスキルの中身を覗いてみましょう。スキルは大きく「概要」と「本文」に分かれていて、概要はYAML、本文はMarkdownで書かれています。ポイントは、AIはまず概要だけを見て「このスキルを今使うべきか」を判断するということ。スキルがどれだけ増えても、最初に読むのは概要だけなので、トークンを無駄に使いません。使うと決めたときだけ本文を読み、必要なら関連ファイルまで見にいく、という流れです。

## スライド9: 段階的開示 ― 関連ファイルと料理本のたとえ

**スライドに載せる内容**
- scripts: 関数やコード
- reference: 本文に入りきらないルール（本文は500行が目安）
- assets: テンプレート・画像・データ
- 料理本のたとえ: 背表紙で本を選ぶ → レシピを読む → 計量スプーンを使う
- 実際に使ったスキルの分しかトークンを使わない

**台本**
この「必要なときだけ深く見る」仕組みを「段階的開示」と呼びます。関連ファイルは3種類。スクリプトには関数やコードを、リファレンスには本文に入りきらなかったルールを——本文は500行に収めるのが推奨なので、あふれた分はここへ。そしてアセットにはテンプレートや画像、データを入れます。料理本でたとえるなら、まず本棚の背表紙を見てどの本が必要か選び、開いてレシピを読み、必要になったら計量スプーンのような道具を取り出す。この仕組みのおかげで、スキルがいくら増えても、実際に使ったスキルの分しかトークンを使わずに済みます。

## スライド10: CLAUDE.md との違い

**スライドに載せる内容**
- CLAUDE.md＝プロジェクト全体の概要・ルール／"常時"参照される
- Skill＝"必要なとき"だけ参照される
- 使い分け: 全体に効かせたいルール→CLAUDE.md、特定タスクのやり方→Skill

**台本**
似たものに「CLAUDE.md」があります。これはプロジェクト全体の概要やルールをまとめたもので、"常に"参照されるのが特徴です。一方スキルは、必要なときだけ参照される。常時か、必要時か——ここが両者の明確な役割の違いです。全体に効かせたいルールはCLAUDE.mdへ、特定のタスクのやり方はスキルへ、と使い分けます。

## スライド11: Skillで何ができるのか

**スライドに載せる内容**
- 会社特有の知識（暗黙知・過去の教訓）を持たせる
- スクリプトでファイル生成・正確な数値集計
- ワークフローの統一（毎回同じ手順・同じ品質）

**台本**
スキルでできることを整理しましょう。ひとつは、会社特有の専門知識を持たせること。「この取引先とは数字の話を多めに」とか「この案件はスケジュール最優先」といった、現場の暗黙知や過去の教訓まで与えられます。ふたつ目は、スクリプトを使ったファイル生成や、正確な数値の集計。AIが苦手な"きっちりした計算"も任せられます。みっつ目は、ワークフローの統一。毎回、同じ手順・同じ品質でタスクを実行してくれます。

## スライド12: 能力レイヤー vs プロセスレイヤー（2章のまとめ）

**スライドに載せる内容**
- MCP / CLI ＝「能力レイヤー」（何ができるか）
- Skill ＝「プロセスレイヤー」（どうやるか）
- 対立ではなく役割が違う／接続手段の選択はケースバイケース

**台本**
ここまでをレイヤーで整理すると分かりやすいです。MCPやCLIは「何ができるか」という"能力レイヤー"を提供します。一方スキルは「どうやるか」という"プロセスレイヤー"を提供する。つまり両者は対立するものではなく、役割が違うんです。外部とつなぐ手段は能力レイヤーから、その手順はプロセスレイヤーから。どちらの接続手段を使うかはケースバイケースで選べばいい、というのが2章の結論です。

## スライド13: スキルを作るスキル（skill-creator）

**スライドに載せる内容**
- 「作りたいもの」を伝える → ヒアリング → 作成
- テストも自動生成し、テスト→改善のループで最適化
- 概要文（ディスクリプション）の最適化までやってくれる

**台本**
ここで、ぜひ紹介したいスキルがあります。「スキルを作るスキル」です。これがとても優秀で、「こういうものを作りたい」と伝えると、いくつかヒアリングをした上でスキルを作ってくれます。しかもテストまで自動で用意して、テストと改善のループを回しながら最適なものに仕上げてくれる。さらに、AIがいつそのスキルを使うべきか判断するための"概要文"の最適化までやってくれます。スキルづくりのハードルが、これでぐっと下がります。

## スライド14: 公開スキルを使うときの注意点

**スライドに載せる内容**
- 便利なスキルは多数公開されている（検索強化、手順書自動生成、スキルを探すスキル等）
- 大切なのは「信頼できる公式から出ているスキルを使う」こと
- 理由: スキルはAIに手順や権限を与えるもの → 出どころ不明は危険

**台本**
最後に注意点をひとつ。世の中には便利なスキルがすでにたくさん公開されています。たとえば検索精度を上げるものや、操作手順書を自動で作ってくれるもの。スキルを探すためのスキルまであります。ただ、ここで大事なのは「信頼できる公式から出ているスキルを使う」ということ。スキルはAIに手順や権限を与えるものなので、出どころの分からないスキルには注意が必要です。
